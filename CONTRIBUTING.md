# Contributing Guidelines

Thank you for your interest in improving _Kaguya_.

We fully embrace AI-powered development, but we are strict about the quality of
software we distribute to users. AI-generated code is welcome only when it is
reviewed, understood, tested, and owned by the contributor submitting it.

This document describes the standards contributors should keep in mind during
development. PR checklists, bug forms, and release-specific prompts belong in
GitHub templates; this file is the durable quality contract for the project.

## Raising Bugs and Giving Suggestions

We use GitHub Issues for bug reports, feature requests, design concerns, and
implementation questions.

- Search for similar or related issues before opening a new one.
- Fill out the relevant issue template as completely as possible when templates
  are available.
- Include the operating system, component, command, logs, traceback, or protocol
  message needed to reproduce the problem.

## Project Standards

- Preserve the component boundaries: Rust Gateway and Supervisor, Python voice
  service, and the planned TypeScript Reasoner.
- Keep privacy and local execution as default assumptions. Do not add external
  services to core flows without a clear opt-in path.
- Treat proto schemas as the shared contracts across components. Kaguya is
  unpublished: update all producers and consumers together instead of retaining
  old fields, aliases, migration paths, or compatibility adapters.
- Avoid OS-specific behavior unless it is isolated, documented, and covered by
  a cross-platform fallback.
- Prefer small, reviewable changes with focused tests over broad rewrites. 
  Large PRs slow down our mission.
- Do not hand-edit generated artifacts. Update the schema or generator and
  regenerate the output.
- Document behavior changes that affect contributors, operators, or downstream
  integrations.

## Developer Console

We encourage you to test your code in real user flows using the local developer console.
It may reveal issues with endpoint I/O, conversation flow, text commands, audio forwarding,
metadata rendering, barge-in, or user-visible behavior.

Note, however, that the console is not perfect. Treat the logs, output, and demonstrated 
behavior of the console only as reference, not as a source of truth.

Running and checking the developer console after initializing a local deployment:

```sh
cd console
npm ci
npm test
npm run build
npm run dev -- --runtime-config ../config/kaguya.local.toml
``` 

## Gateway

The Gateway is the deterministic Rust orchestrator. It owns event priority,
conversation state, RAG memory coordination, tool dispatch, endpoint surfaces,
and clients for adjacent processes.

Quality guarantees:

- Keep routing deterministic. The Gateway should not ask an LLM to decide core
  orchestration behavior.
- Preserve P0-P5 event priority semantics and cancellation behavior.
- Be careful with async backpressure, channel bounds, task lifetimes, and
  shutdown paths.
- Keep module ownership clear and update callers directly when moving a module.
- Add or update tests for changes to event routing, memory persistence,
  retrieval behavior, path safety, or protocol handling.
- Regenerate or rebuild Rust proto bindings through `cargo build` (the
  `kaguya-protocol` crate generates them for the workspace); do not edit
  generated tonic output manually.
- Keep `kaguya-protocol` limited to the wire contract: generated protobuf code
  and its validated types. Gateway and Supervisor must not depend on each other
  outside tests.

Verification:

```sh
cargo fmt --all --check
cargo test -p kaguya-protocol
cd gateway
cargo test --all-targets
```

Useful development commands:

```sh
cd gateway
cargo fmt
cargo build
cargo test
```

## Talker

The Talker owns voice I/O, turn detection, LLM prompting, TTS, and the fast-path
agent runtime. Its tests must remain runnable without requiring a GPU, live
microphone, TTS engine, or local model server.

Quality guarantees:

- Keep lightweight imports lightweight. Tests should be able to import authored
  modules without pulling in heavyweight voice or model runtimes unless the test
  is explicitly scoped to that integration.
- Avoid blocking work in async paths. Isolate blocking audio and model
  operations behind clear boundaries.
- Preserve barge-in, turn detection, and sentence-streaming behavior when
  changing listener, speaker, or inference code.
- Keep generated proto stubs in `talker/proto/` generated by
  `talker/scripts/gen_proto.py`.
- Add focused tests for prompt formatting, turn detection, gRPC protocol
  handling, and threading behavior when those surfaces change.

Verification:

```sh
cd talker
uvx ruff check .
uvx ruff format --check .
uv venv
uv pip install pydantic-settings opuslib grpcio protobuf httpx pytest pytest-asyncio
uv run --no-project pytest tests/ -v
```

Type checking:

```sh
cd talker
uv venv
uv pip install pydantic-settings opuslib grpcio httpx mypy
uv run --no-project mypy config.py binding.py main.py server.py voice/ inference/ --ignore-missing-imports
```

Proto regeneration:

```sh
cd talker
uv run python scripts/gen_proto.py
```

## Reasoner

The Reasoner service is not implemented. Its planned boundary is documented in
`reasoner/README.md`; the Gateway client and protobuf contract already exist.

Quality guarantees:

- Do not imply Reasoner capabilities that are not implemented.
- Preserve the intended boundary: Reasoner handles long-running delegation and
  streamed progress; Gateway remains the orchestrator.
- When adding implementation, include cancellation, process-boundary, and
  protocol-shape tests early.
- Add a package, lockfile, tests, and a TypeScript build gate with the service
  implementation. An empty package or skipped test command is not validation.

## Proto Changes

Proto files are shared contracts. A schema change can break all three
components.

Quality guarantees:

- Change field names, numbers, and shapes directly when the contract needs it.
  There are no published wire or persisted-data compatibility obligations.
- Update every affected producer, consumer, test, and specification in the same
  change. Do not retain obsolete fields or reserve them solely for compatibility.
- Run linting and generation after proto edits.

Verification:

```sh
buf lint proto/
make proto
```

## Repository-Wide Verification

Use repository-wide commands before opening larger PRs or when a change crosses
component boundaries.

```sh
make proto
make test
make lint
make format
```

Component-specific commands are preferred while developing because they are
faster and closer to the CI job that owns each component.
